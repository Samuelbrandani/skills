# Agent notes — Claude Code, Codex, Cursor and others

`SKILL.md` is written against the Agent Skills standard, so the method is the same everywhere. What changes between agents is the **harness**: how the Figma MCP is authorized, what the tools are called, how the agent asks the user a question, and what happens when a tool result is too big. This file is the translation table. Read the row for your agent once; the phases in `SKILL.md` refer to these rows.

| Need | Claude Code | Codex (CLI / IDE / app) | Cursor, Gemini CLI, others |
|---|---|---|---|
| **Install the skill** | `npx skills add Samuelbrandani/skills --skill figma-flutter -g` → `~/.claude/skills/` (or `.claude/skills/`) | `npx skills add Samuelbrandani/skills --skill figma-flutter -a codex` → `~/.agents/skills/` (repo scope: `.agents/skills/`). Codex re-scans skills automatically; restart if it does not show up | same CLI with `-a <agent>`; the CLI knows 80+ agents |
| **Invoke** | automatic on a Figma link, or `/figma-flutter` | automatic when the request matches the description, or `$figma-flutter` | automatic, or the agent's own mention syntax |
| **Figma MCP: connect** | the `figma` plugin or an MCP entry pointing at `https://mcp.figma.com/mcp` | in `~/.codex/config.toml`: `[features] rmcp_client = true` and `[mcp_servers.figma] url = "https://mcp.figma.com/mcp"` with `auth = "oauth"` (then `codex mcp login figma`) or `bearer_token_env_var = "FIGMA_OAUTH_TOKEN"`; in the Codex app: Plugins → Figma → Install | the agent's MCP config with the same URL |
| **Figma MCP: authorize (phase 0)** | if only `authenticate`/`complete_authentication` exist, call `authenticate`, give the user the URL, then load the real tools with `ToolSearch("select:mcp__figma__whoami,…")` | `codex mcp login figma` in a terminal, or set `FIGMA_OAUTH_TOKEN`; then restart the session. No in-chat OAuth flow | per agent; usually a login command or a token |
| **Tool names** | `mcp__figma__get_metadata`, `mcp__figma__get_design_context`, … | the same tools, exposed under the server name (`figma`) — call them by their bare name (`get_metadata`) when the agent lists them that way | idem |
| **`figma-design-to-code` prerequisite of `get_design_context`** | `ReadMcpResourceTool(server: "figma", uri: "skill://figma/figma-design-to-code/SKILL.md")`, then `skillNames: "resource:figma-design-to-code"` | Codex cannot read MCP resources from chat. Install the curated skill (`npx skills add openai/skills --skill figma -a codex`) or the Figma plugin; the parameter `skillNames` is for logging and the call works without it — do not stall on it | if the agent has no resource reader, proceed as Codex |
| **Big tool results** (`get_metadata` on a section, `get_design_context` on a whole screen) | the harness saves the result to a file; run `scripts/figma_outline.py <file>` on it | the result is **truncated** by a token budget. Call `get_metadata` per screen frame (not per section), and `get_design_context` per section of a screen (header, body, footer). Raise the budget in `config.toml` if needed: `[mcp_servers.figma.tools.get_metadata] output_token_limit = 60000`. If you can paste a saved result into a file, `figma_outline.py` still works on it | idem: smaller nodes first |
| **Screenshots and asset downloads** (`curl -L -o`) | plain shell | the sandbox may block network; approve the `curl` when asked, or switch the sandbox to allow network for the session. URLs expire in minutes, so download right after the tool returns | idem |
| **Ask the user the decision batch** | one `AskUserQuestion` with the four decisions | write the four decisions as a numbered list in chat, with the recommended option first, and wait for the answer before phase 3 | idem, in chat |
| **Plan before code** (repo `CLAUDE.md`/`AGENTS.md` says so) | `EnterPlanMode`, write the plan with `references/plan-template.md`, `ExitPlanMode` for approval | write the plan file (`docs/plans/…` per the template), show it, and wait for an explicit "go" in chat before phase 6 | idem |
| **Run the bundled scripts** | Bash tool | shell tool inside the sandbox; the scripts are read-only and need no network. On Windows use `py -3 scripts\repo_scan.py` or `scripts\repo_scan.ps1` | idem |
| **Design probe tests** | `flutter test` via Bash | `flutter test` via shell; the first run may need approval to write `test/design/snapshots/*.json` | idem |
| **Repo instructions file** | `CLAUDE.md` (and parents) | `AGENTS.md` (and parents); the scanner lists both | the agent's own file; the scanner lists `CLAUDE.md`, `AGENTS.md`, `ARCHITECTURE.md` |

Things that do not change: the phases, the three mapping tables, the asset rules, the data contract, the 12 axes, the gates.
